# Restricted staging enforcement inventory

Status: **hosted commerce remains disabled**. This is an inventory of the current boundary, not a claim that synthetic staging controls have been integrated. The database attestation helper reads the connection identity and marker in one SQL statement; it does not bind later commerce queries or transactions to that connection.

| Entry point                                                                | Existing control                                                                                                                                                                       | Missing for restricted staging                                                                                                                  |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `/api/commerce` GET/POST and `store.ts` operations                         | Staging site auth; synchronous local-only commerce guard; shopper ownership and transaction checks.                                                                                    | Per-operation attestation on the actual connection, provisioned synthetic principal/order checks, isolated payment/notification/storage policy. |
| `/api/customer-auth/[...all]` and `customer-auth.ts`                       | Site auth and local-only commerce guard; Better Auth sessions and database-backed rate limiting. The `.invalid` email rule is client-controllable and is **not** synthetic enrollment. | Server-controlled enrollment, session and provisioning checks; deny public enrollment.                                                          |
| `/api/admin/commerce` and `admin.ts`, `factory.ts`                         | Site auth; local-only guard before actor lookup; role and financial grants.                                                                                                            | Attested execution context and independently enrolled synthetic staff on all reads and writes.                                                  |
| `/api/admin/reports` and `reports.ts`                                      | Site auth; local-only guard before session lookup; owner authorization, rate limits and report limits.                                                                                 | Per-operation database attestation and synthetic owner authorization.                                                                           |
| `/api/commerce/payment-evidence` and `evidence.ts`                         | Site auth; local-only guard; ownership/permission checks, viewer-bound expiring signature and private S3 object.                                                                       | Attested operation, synthetic shopper and independently verified staging bucket identity/policy.                                                |
| `/api/mock-payments/webhook` and `payments.ts`                             | Site auth; local-only guard in service; mock signatures, idempotency and transition checks.                                                                                            | Explicit staging provider/credential isolation and synthetic payment enforcement.                                                               |
| `scripts/phase3-jobs.ts`, `notifications.ts`                               | Local-only guard; local test-notification capture and outbox lease.                                                                                                                    | Verified synthetic worker identity, staged connection and transport restrictions on every job.                                                  |
| `src/app/admin/actions.ts` and admin media handlers                        | Phase 2 permission/session checks and staging site auth via session; independent of commerce guard.                                                                                    | Explicit staging database/identity checks before any session side effects, catalog/inventory/admin writes or uploads.                           |
| Admin order/settings/report pages and customer cart/account/checkout pages | `commerceEnabled()` controls rendering; server APIs recheck separately.                                                                                                                | Runtime mode tied to actual attested execution and synthetic principal; no UI flag may authorize operations.                                    |
| Storefront product page and catalog services                               | Publication/catalog-source checks; product page conditionally reads variants when commerce is enabled.                                                                                 | Verify staging isolation before any database-backed staged catalog reads; prevent access to production data.                                    |

Do not enable `restricted_staging` or infer safety from an environment name. The unresolved technical requirement is a database execution design that verifies the identity of the actual connection used for every relevant read/write and transaction, plus immutable server-controlled synthetic identity enrollment and dedicated storage/payment/notification isolation. A single preliminary check on a pooled client is not enough: subsequent operations can use a different connection, and checking before a mutation cannot undo an unsafe mutation if the connection changes. The implementation must also cover direct server actions, Better Auth callbacks, workers and non-commerce administrative APIs. Each must be tested for absence of prohibited side effects on failure.
