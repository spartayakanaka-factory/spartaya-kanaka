# Restricted staging runtime — PARTIAL / disabled

`src/lib/commerce/runtime.ts` currently admits only explicit local simulation, mock payment mode and a fixed list of loopback disposable databases on port 33078. It rejects staging and production, including reporting and financial actions. This remains in force.

The requested hosted simulation cannot safely be enabled by substituting a database hostname or environment flag: current customer and checkout records are not proven synthetic, hPanel does not show an attached database or private media storage, the host-level robots path differs from the application, and valid-credential routing has not been verified. A staging marker or database name alone cannot prove that a database or storage account contains no real data. Production denial, Basic Auth, per-action authorization, mock-only payments and local notification capture must not be relaxed.

Before an implementation can safely admit hosted staging, define and test a trusted staging identity anchored to a specifically authorized database and isolated private storage, enforce synthetic-only accounts and order data at every write boundary, enforce mock-only gateways and a notification sink, independently verify access protection, and prevent accidental use of production credentials. Its migration/identity controls must remain separate from runtime authorization. Test missing or conflicting variables, wrong database/user/endpoint, production, invalid auth, real provider and notification attempts, cross-user authorization, private evidence and rate-limit failure. A future reviewed implementation must pass an end-to-end synthetic hosted test after separate deployment and migration approvals. Current local tests do not constitute that test.
