# Staging database attestation — building block only

`src/lib/server/commerce/staging-database-identity.ts` provides a read-only, fail-closed attestation helper. It is deliberately **not wired into commerce** and does not activate hosted staging. It checks explicit staging flags and mock payment mode; exact configured URL host, port, database and user; the connected server's `DATABASE()`, `CURRENT_USER()` and port; and a separately provisioned HMAC-authenticated random marker. Query parameters are bound, and all failures return an opaque error. The helper never creates a marker or changes data.

Configuration names for the proposed contract are `APP_ENV`, `STAGING_SITE`, `STAGING_DATABASE_APPROVED`, `PAYMENT_MODE`, `DATABASE_URL`, `STAGING_DB_HOST`, `STAGING_DB_PORT`, `STAGING_DB_NAME`, `STAGING_DB_USER`, `STAGING_DB_MARKER_ID`, and `STAGING_DB_MARKER_SECRET`. The marker ID must be 32 random bytes encoded as lowercase hex; the marker secret must be privately generated and at least 32 characters. `STAGING_DATABASE_APPROVED=1` is only a configuration assertion, not evidence of owner approval. Credentials and marker secrets must never enter Git, documentation or logs.

For review, the expected table is `staging_identity` with a unique `marker_id` and a 64-character lowercase-hex `signature`. Its signature is HMAC-SHA256 over the JSON array `["sprtaya-staging-v1", markerId, host, numericPort, databaseName, runtimeUser]` using the private marker secret. The test creates a session-scoped temporary table in the existing exact local disposable test database and checks success, tampering and connection failure. Unit tests cover missing or conflicting configuration, wrong target/user/port and marker mismatch.

**No permanent migration or marker initialization procedure has been approved or implemented.** Before provisioning, separately review database ownership, access, TLS, exact identity, privilege separation, marker lifecycle, backup/restore and a secure initialization tool; then obtain explicit approval for the precise persistent operations. Never initialize a marker in a production or uncertain database. A signed marker can be copied with a database backup and an attacker who controls both configuration and the secret can defeat this check; this is not proof of synthetic data, private storage, safe accounts, or the absence of production credentials. Bind the eventual design to operational access controls and separately verify restored identities.

The runtime database adapter currently uses a pool of 5, 10-second acquisition/connect timeouts and 60-second idle timeout. TLS requirements for the actual Hostinger path and separate runtime-versus-migration least privileges remain unverified. Do not configure staging until the complete synthetic-only boundary and provider isolation are implemented and reviewed.
