For SR-1, infrastructure-enforced least privilege is the simpler candidate compared with connection-bound attestation on every Prisma operation. The local probe demonstrates that MariaDB enforces the tested grants across pooled connections and transactions. It does **not** show that the app is wired to use those credentials, that the data is synthetic, or that a Hostinger user cannot access production. A staging deployment would need independently verified dedicated credentials, server-side role and identity isolation, private storage and mock-only provider controls; a signed marker alone is insufficient. The alternative connection-bound design would need to bind the checked connection to every actual database operation and cover nested transactions, direct actions and worker entry points.

Prisma documents that extension code calling a client-level method from inside a transaction can issue its query on a **new connection** outside that transaction. A naive `$extends` wrapper that calls a base client's `$queryRaw` for attestation therefore does not establish transaction-bound identity. See [Prisma 7 shared extension limitations](https://www.prisma.io/docs/orm/v7/prisma-client/client-extensions/shared-extensions). This is a specific reason that wrapper was not added or treated as a completed runtime.
