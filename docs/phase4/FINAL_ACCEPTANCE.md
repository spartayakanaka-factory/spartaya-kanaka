# Phase 4 final local engineering acceptance

**PHASE 4 LOCAL ACCEPTANCE: PARTIAL.** The approved scope is one factory, not a multi-tenant platform; no tenant schema or business switch was added. Real customer, owner and staff authorization are independently enforced. A partial decision remains necessary because the measured report workload does not include refunds, multi-day peaks or concurrent users and no index migration or recovery rehearsal has been completed. Deleted-account, actual network/backend outage through the route, keyboard chart interactions, and dependency vulnerability audit remain incomplete. Do not promote or deploy on this evidence.

## Implementation and security

The existing owner-only report retains its verified financial definitions, local-only commerce guard and 31-day range/5,000-record limits. Charts show daily order count and gross verified collection, verified payment-method amounts, active ready-made versus made-to-order units and top-product ordered units. Accompanying tables and text carry exact values. Daily order counts include cancelled orders by order creation day; money uses verified/reconciled event day. No financial or business policy was changed and no new dependencies were introduced.

The process-local rate limiter was replaced by an atomic fixed-window upsert into the existing `auth_rate_limits` table. Keys are namespaced SHA-256 hashes of owner IDs, never session credentials. MariaDB row locking enforces a shared threshold across instances and database time controls the window. It runs after owner authentication and before filter validation, so malformed filters consume the same allowance. Failure of the backing database propagates to a generic error rather than bypassing the limit. This operational counter is a write, while reporting remains financially read-only. The table retains at most one such row per distinct owner identity ever seen; removal/retention for deleted owners needs an explicit operational policy. Do not claim a distributed limiter across independently replicated databases.

In a real local production server, anonymous and manager requests are denied, and a real signed-in synthetic customer receives no financial data. Tampered cookies, a forged owner header and malformed authorization are denied. An owner can access the report; banning, expiry and revocation block an existing owner session. Owner identity is revalidated against the database inside the report transaction. Suspension maps to the existing `banned` property; no separate suspension model exists. Other unauthorized-session cases remain as stated above.

## Financial and performance evidence

Financial aggregation uses integer minor units, verifies canonical receipt/refund records and fails closed for contradictory or duplicate facts. The real MariaDB fixtures include reconciled and unpaid COD, verified and claimed wallet/InstaPay, partial payments, advances and reconciled refunds; existing commerce integration coverage also tests the underlying workflows. See `closeout-regression.json` and the earlier `acceptance.md` for scope and definitions. No actual bank, card or carrier settlement was exercised.

`workload-benchmark.json` records actual `ownerReport` calls against 100, 1,000 and 4,000 synthetic orders and line items, mixing wallet, InstaPay, unpaid COD and reconciled COD. Exact collection and outstanding totals were checked. On this local MariaDB, the calls took 70 / 119 / 382 ms, with Node heap deltas of approximately 1.3 / 3.2 / 65.2 MB. These are single runs, not percentiles; garbage collection makes the heap deltas approximate. The workload is concentrated in one day and does not include refunds, multi-day peak ranges or concurrent report users. Synthetic benchmark orders and financial records were removed after each measurement; synthetic product and owner records remain in the disposable test database.

`benchmark.json` records MariaDB 11.8.9 `ANALYZE FORMAT=JSON` over isolated **temporary** synthetic event tables. At 1,000 / 20,000 / 100,000 rows, unindexed query execution was approximately 0.34 / 7.35 / 38.50 ms; with `(kind, createdAt)` it was 0.05 / 0.32 / 0.97 ms, examining 0 / 209 / 1,045 matching rows versus 1,000 / 20,000 / 100,000 scanned. The small case has no matching events. These measurements include neither joins, all report queries, concurrency nor production-sized line items and do not establish a service-level performance target. Existing query plans and bounded responses remain in `query-plan.json`; an event index looks justified but requires a reviewed additive migration, a verified backup/restore rehearsal and representative workload tests before acceptance. Index maintenance adds write overhead. No migration was created or applied in this closeout; the structure of the disposable schemas is unchanged and no hosted database was accessed. Synthetic data and reporting counters were written only in the disposable schemas.
