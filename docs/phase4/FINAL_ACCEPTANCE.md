## Exact validation and interpretation

- **Automated regression:** 230 passed, zero failed or skipped. Of these, 105 cases are in integration-named files and two further limiter cases use real disposable MariaDB. Ninety-one of those integration-named cases are in files that mock Next.js request context; they also use real database services, so these categories overlap. One additional limiter-failure case mocks the storage backend. The suites include real local S3-compatible storage exercises; an exclusive per-case storage count was not recorded. Nine reporting integration tests were also rerun on the restored indexed schema, separate from the 230.
- **Browser/accessibility:** 28 production-mode browser checks passed, including real customer, banned, deleted, expired and revoked sessions, report totals, keyboard focus, concurrency and interruption. Six axe audits at 390/768/1440 in Arabic and English had zero violations. These tests do not cover every browser or assistive technology.
- **Financial:** the 100-order, 31-day synthetic workload's expected and actual totals match: 600,000 minor units collected, 80,000 refunded, 520,000 net and 300,000 outstanding. It included 60 reconciled and 40 pending refunds. These are synthetic records, not live settlements.
- **Concurrency:** 36 requests at concurrency six from two owner sessions yielded 30 successes, six intended 429s and no other errors; median 31 ms and empirical p95 361 ms in that run. Four independent Node clients made 12 successful authenticated requests.
- **Performance:** on Apple M1, 8 GB RAM, macOS 15.6.1, Node 22.23.4 and local MariaDB 11.8.9, each size had two warm-ups and seven measured iterations. On the indexed recovery schema, 100 / 1,000 / 4,000 / 4,900 orders had median 26 / 97 / 297 / 353 ms and empirical p95 29 / 111 / 325 / 364 ms. Seven-sample p95 is the sample maximum, not a statistically reliable production percentile. At 4,900 orders sampled peak process heap was about 237 MB, including the fixture generator; forced-GC deltas and all raw timings are recorded in `workload-indexed.json`. Prisma query-event durations include driver and transport overhead; elapsed minus their sum estimates non-query wall time. Node CPU time includes all Node threads and driver work, not database-server CPU.
- **Query review:** the event `(kind, createdAt)` and order `createdAt` indexes improve selective date access. MariaDB still selected a primary scan for the highly concentrated 4,900-order date. The pending-payment grouping plan scans payment rows and uses temporary grouping; it took approximately 3–5 ms in these local fixtures. Extra indexes incur storage and write costs; review payment-state indexing against representative staging volumes rather than assuming this small sample proves its need.
- **Outages:** a nonresponsive handshake returned 503 for five concurrent requests in about 5.5 seconds with one observed socket; an unavailable limiter table and an interrupted locked query failed closed and recovered. The entire *separate* test MariaDB was stopped while an authenticated request was waiting; it returned 403 without financial data, then the service and session recovered. That separate database is deliberately excluded by the commerce target guard, so report recovery was verified separately after restoring the approved local target. The shared Phase 2–4 database process was never stopped.
- **Security:** the current pnpm advisory audit returned no advisories. A synthetic local session cookie appeared in a failed test diagnostic; all synthetic owner sessions were immediately revoked and later test error handling suppresses private request details. The final scoped secret/preservation scan is recorded in `final-security-and-preservation.json`. No production credentials were accessed.

## Migration and recovery

The migration is `prisma/migrations/20261031000000_phase4_report_indexes/migration.sql`; `docs/phase4/migration-manifest.json` records its hash and the reviewed six predecessors. A private mode-0600 dump of the disposable test schema is retained under `.local/phase4/runtime/database/backups/`; its SHA-256 is in `recovery-evidence.json`. The exact artifact was restored to a new disposable recovery schema: 47 table inventories and all data matched before migration; all pre-existing business-table data matched after migration, with the migration ledger separately verified. The report digest matched, nine reporting tests passed, and a second deploy found no pending migrations. The first rehearsal had an out-of-order migration name; it was corrected and the complete rehearsal repeated in a fresh recovery schema, with earlier disposable copies preserved.

For any later authorized staging exercise, independently verify the target and migration ledger, take and verify a recoverable staging backup, review this additive index migration and its write overhead, and follow the separately approved migration procedure. Forward recovery or restoring the verified backup requires its own review; do not point local rehearsal scripts at hosted databases.
